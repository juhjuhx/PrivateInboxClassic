# 通知去重（NOTIFICATION-DEDUP）

> 分支：`fix/x200pro-notification-burst`　基準：`8494910`
> 狀態：**已實作並量測**

---

## 1. 核心問題

Android 的通知系統是**更新**式的，不是**追加**式的。
同一則群組通知會被反覆更新，每次都帶著**累積的訊息歷史**。

| 修訂 | 通知呈現 | 其中是新的 |
|------|---------|-----------|
| 1 | 1 則 | 1 則 |
| 2 | 2 則 | 1 則 |
| 3 | 3 則 | 1 則 |
| … | … | … |

所以有**兩���**去重問題，必須分開解決：

| 問題 | 層級 | 解法 |
|------|------|------|
| 同一則訊息被重複保存 | 資料庫 | 去重**指紋** |
| 整段歷史被重複寫入 | 管線 | 已寫入訊息的**記憶** |

## 2. 去重指紋

### 2.1 組成

```
fingerprint = HMAC-SHA256(
    packageName ‖ 0 ‖ timestamp ‖ 0 ‖ title ‖ 0 ‖ sender ‖ 0 ‖ body ‖ [0 ‖ discriminator]
)
```

| 欄位 | 來源 | 為什麼 |
|------|------|--------|
| `packageName` | 通知 | 同一則文字在不同 App 是不同訊息 |
| `timestamp` | 來源的原始時間戳 | 最強的身分識別。**沒有時用 0** |
| `title` | 通知 | 同一個對話 |
| `sender` | 通知 | 同一個對話裡的不同人 |
| `body` | 通知 | 內容 |
| `discriminator` | **只在沒有時間戳時** | 區分兩則**內容相同**的不同訊息 |

### 2.2 沒有時間戳時的 fallback

**這是本專案修過兩次的缺陷。**

| 版本 | fallback | 結果 |
|------|----------|------|
| v0.4.0 | **擷取時間** | ❌ 擷取時間是**每則通知**一個，同一則通知裡的所有訊息算出**同一個鍵** → 100 則訊息只存 20 列 |
| v0.4.1（第一次修） | 訊息在歷史中的**索引** | ❌ 平台的歷史上限是 25 則，超過後**每則訊息都會位移** → 第 26 則以後永遠抓不到 |
| **v0.4.2（現在）** | **訊息自身的內容與寄件者** | ✅ 跨修訂穩定，兩則不同訊息必定不同 |

現在的規則：

```kotlin
val hasSourceTimestamp = sourceTimestamp > 0
val dedupTs = if (hasSourceTimestamp) sourceTimestamp else 0L
val dedupExtra = if (hasSourceTimestamp) "" else messageDiscriminator
```

**有時間戳時，指紋與舊版位元級相同** ——
所以已經存進去的訊息**不會**因為升級而被重新收錄。

### 2.3 discriminator 的內容

```
有時間戳：  "ts:<時間戳>"
沒有時間戳："c:<索引>:<寄件者>:<內文>"
```

**為什麼沒有時間戳時還保留索引**：
索引在平台上限（25 則）之內是穩定的，超過會位移。
把它放進去是為了讓**同一則訊息**在位移前後仍有機會被辨識為同一則 ——
但主要的辨識力來自寄件者與內文。

## 3. 寫入放大：記憶區

### 3.1 問題

一個 500 則訊息的群組會呈現 9,500 則訊息（10 個對話 × sum(1..50)）。
原本每一則都會被送去寫入，而每次寫入在發現重複之前都先做了一次
**AES-GCM 加密**。

```
9,500 次 CryptoStore.seal()  →  500 列真正入庫，9,000 次浪費
```

### 3.2 解法

Listener 記住「這則通知的哪些訊息已經寫入過」，只提交新的那些。

| 項目 | 設計 |
|------|------|
| Key | 通知的 `sbn.key`（`<userId>\|<pkg>\|<uid>\|<tag>\|<id>`）|
| 生命週期 | 通知被移除時（`onNotificationRemoved`）刪除 |
| 上限 | 每則通知 4,000 個識別碼，超過就重置 |
| 執行緒 | `ConcurrentHashMap` |

### 3.3 效果

| 指標 | 修正前 | 修正後 |
|------|--------|--------|
| `messages_presented` | 9,500 | 9,500 |
| `messages_submitted` | 250 | **500** |
| `messages_saved` | 250 | **500** |
| `unaccounted` | 3,821 | **0** |
| 加密次數 | 9,500 | **500** |

## 4. 邊界情境

Brief 要求的八個情境，逐一回應：

| # | 情境 | 行為 | 驗證 |
|---|------|------|------|
| A | 同一群組連續傳送**不同**內容 | 全部保存 | TEST-A |
| B | 同一群組連續傳送**相同**文字 | 全部保存（用索引區分）| TEST-D |
| C | **兩個群組同時**傳送相同文字 | 分開保存，對話不串台 | TEST-D |
| D | 同一通知被來源更新 | 只保存新的訊息 | TEST-E |
| E | MessagingStyle 每次包含歷史 | 歷史只存一次 | TEST-F |
| F | 群組摘要與子通知同時出現 | 摘要跳過、子項保存 | TEST-J |
| G | 來源時間戳相同 | 靠寄件者 + 內文 + 索引區分 | TEST-D |
| H | 通知短時間內消失或被覆蓋 | 無法復原（平台限制），但 `onNotificationRemoved` 會清理記憶 | — |

### 4.1 情境 C 的特別說明

兩個群組傳送**完全相同**的文字。舊版的 `associate { body to key }`
會把它們混為一談。新版的驗證是：

- 每個對話有**自己的 key**（3 個 key，不是 1 個）
- 每個 key 底下有正確數量的列
- **同一段文字存在於每一個 key 底下**

這是「沒有合併」的正向證明，而不是「沒有合併」的推論。

### 4.2 情境 H：平台的 25 則上限

`Notification.MessagingStyle` 只保留**最多 25 則訊息**（AOSP 的
`Notification.MAX_MESSAGES = 25`）。

**第 26 則以後的訊息，任何 App 都收不到** —— 通知本身沒有攜帶它們。

量測證實了這個上限：10 個對話各 50 則更新，呈現的訊息總數是
9,500 = 10 × sum(min(i, 25))，**完全吻合**。

**實務上的影響有限**：群組一次來 30 則時，前 25 則會被截斷，
但每一則訊息都是**獨立的一次修訂**被送達，實務上每一則都會在
某一次修訂中出現在歷史裡而被擷取到。
只有當 26 則以上**在同一次修訂內同時到達**時，第 26 則才會被丟棄。

這是**平台限制，不是本 App 的缺陷**，因此測試的期望值是
「系統實際暴露的訊息數」，不是「測試送出的訊息數」。

## 5. 跨語言一致性

訊息 id 必須在 Android 與 Python 兩邊**完全相同**，否則匯入不冪等。

**本輪找到的真實缺陷**：

```
python:  msg_vAqh2ijUIiDWkO4grhsE
android: msg_vAqh2ijUIiDWkO4grhsE\n
```

Android 的 `Base64` 預設附加**換行**。摘要本身完全相同，
所以**任何只看單一邊的測試都看不到它**。

修正：使用 `URL_SAFE | NO_PADDING | NO_WRAP`，並 trim 掉
padding 與換行。

**這個案例說明為什麼跨語言測試是必要的**，而不是錦上添花。

## 6. 不變條件

```
messages_submitted == messages_saved + messages_deduplicated + messages_failed
```

`unaccounted = messages_submitted − messages_saved − messages_deduplicated`
**必須是 0**。

所有十個突發案例都滿足這個條件。

## 7. 已知的取捨

| 取捨 | 說明 |
|------|------|
| 沒有時間戳且文字相同時，靠索引區分 | 平台的 25 則上限會讓索引位移。位移後可能被視為新訊息而重複收錄 —— **但去重指紋仍含寄件者與內文**，所以指紋相同，資料庫層仍然去重 |
| 記憶區在行程死亡時遺失 | 下次連線時該通知的訊息會被重新提交，但資料庫層的去重會擋住重複 |
| 記憶區的上限會重置 | 超過 4,000 個識別碼時重置，之後可能重複提交（資料庫層仍去重）|

**資料庫層的去重指紋是最後一道防線。** 記憶區是最佳化，不是正確性的依賴。
