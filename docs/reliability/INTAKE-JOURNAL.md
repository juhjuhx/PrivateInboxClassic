# Intake Journal — 設計與證據（INTAKE-JOURNAL）

> 分支：`fix/x200pro-notification-burst`（v0.4.3）
> 狀態：**PROTOTYPE / 未接入正式管線**。
> 本文件記錄的是**量測**與**契約**，不是一個已經接上去的功能。

---

## 1. 為什麼先量測

brief 明確要求：

> `queue_wait p99=2091ms` 不是最大延遲，也不是確定的行程死亡遺失量。
> **不得直接宣稱持久化 Journal 能保證 100% 通知擷取。**

所以本輪先做**行程死亡實驗**，把遺失視窗量出來，再決定是否值得實作。

---

## 2. 實驗

`ProcessDeathExperimentInstrumentedTest`：

| 實驗 | 做什麼 | 量到什麼 |
|------|--------|----------|
| 狀態機完整性 | 枚舉事件狀態，確認終態與非終態的分界 | 契約本身 |
| 遺失視窗 | 用**刻意放慢**的 writer 灌 200 個事件，量**排空時間** | 事件只存在於記憶體的時間 |
| 進行中事件 | writer 被 hold住時，量有多少事件處於非終態 | 行程被殺時會消失的數量 |

### 2.1 量測結果

```
DEATH-WINDOW received=200 queued=1 processing=0 committed=200
             acknowledged=0 failed=0 lost=0
             queued_during_drain=1 drain_ms=5565
```

**`drain_ms=5565` 就是遺失視窗。**

在 writer 被刻意放慢的情況下，200 個事件花 **5.6 秒**才排空。
在這 5.6 秒裡，它們**只存在於記憶體**。
如果行程在這期間被殺，那 200 個事件就全部消失 —— **沒有任何紀錄**。

### 2.2 這個數字代表什麼

| | 值 | 說明 |
|---|-----|------|
| 正常情況的佇列等待 | p99 = 2,091 ms | 上一輪的實測 |
| **放慢 writer 的排空時間** | **5,565 ms** | 本輪的實測 |

**5.6 秒 ≫ 2.1 秒**，因為這次是**刻意**放慢的。
真實情況的視窗會比較短，但**不是零**。

### 2.3 誠實的限制

這個實驗**沒有**真的殺掉行程。它量的是「事件只存在於記憶體的時間」，
而那正是行程被殺時會消失的時間。

**為什麼不真的殺行程**：
在真機上強制殺行程會影響使用者的 App 與資料 —— 這是本專案不做的。
在模擬器上殺行程則與真實的 vivo 背景管理行為不同，
量到的數字會讓人以為有實證。

所以這個實驗給的是**視窗的上界量測**，不是「殺掉行程後遺失幾則」。

## 3. 持久化 Journal 契約

### 3.1 狀態機

```
   RECEIVED ──▶ JOURNALED ──▶ PROCESSING ──┬──▶ COMMITTED     (terminal)
                       │                   ├──▶ ACKNOWLEDGED  (terminal)
                       │                   └──▶ FAILED_RETRYABLE
                       │                              │
                       │                              └──▶ FAILED_TERMINAL (terminal)
                       ▼
                   (行程死亡 → 重啟後重放)
```

| 狀態 | 意義 | 行程死亡後 |
|------|------|-----------|
| `RECEIVED` | listener 看到了，還沒寫入 journal | **遺失** |
| `JOURNALED` | 已寫入 journal，尚未處理 | 重放 |
| `PROCESSING` | worker 正在寫入 | 重放（冪等）|
| `COMMITTED` | 列已入庫 | 刪除 journal 項目 |
| `ACKNOWLEDGED` | 已判定為重複 | 刪除 journal 項目 |
| `FAILED_RETRYABLE` | 寫入失敗，可重試 | 重試（上限內）|
| `FAILED_TERMINAL` | 寫入失敗，不會再試 | 刪除，記錄 |

### 3.2 不可迴避的缺口

**在 `RECEIVED` 與 `JOURNALED` 之間，行程被杀 → 事件遺失。**

因為 listener 回呼必須**極快**返回，把事件寫入 journal 會增加回呼的
I/O —— 而回呼是在**主執行緒**上。

**這是本專案不承諾「零遺失」的原因。**
任何宣稱 100% 擷取保證的設計都是不誠實的，除非它接受主執行緒的
同步寫入延遲。

### 3.3 必須滿足的條件

| 條件 | 說明 |
|------|------|
| **有界容量** | journal 不能無限增長。超過上限時必須明確報錯，不是丟棄 |
| **冪等重放** | 重放同一個事件不能產生兩列 —— 靠現有的去重指紋 |
| **原子提交 / 確認** | journal 項目的刪除必須與資料庫寫入在同一個交易邊界內，或者用「先寫入再刪除」的順序 |
| **重試上限** | 不可重試的失敗要變成 `FAILED_TERMINAL`，不能無限重試 |
| **加密保存** | journal 含有訊息內容，必須用與 `CryptoStore` 相同的方式加密 |
| **低磁碟空間** | 寫入失敗時必須明確處理，不能讓擷取管線崩潰 |
| **重啟復原** | 行程重啟後，journal 必須能重放未完成的事件 |
| **不存未授權的私人資料** | journal 只能存已經被授權擷取的來源 |
| **主執行緒不做無界 I/O** | journal 的寫入必須有界，且不能在主執行緒上做無界的 I/O |

### 3.4 金鑰與資料生命週期

journal 的加密必須**沿用** `CryptoStore` 的金鑰 —— 同一把金鑰、
同一套 AAD 規則。

**後果**：金鑰失效時，journal 裡的內容也無法解密。
這是**一致的**，不是新增的問題：資料庫裡的內容同樣無法解密。

## 4. 為什麼本輪**沒有**接入正式管線

| 理由 | 說明 |
|------|------|
| 收益未經證實 | 遺失視窗量到了（5.6 秒，刻意放慢的情況），但**真實情境**的視窗沒有量到 —— 那需要在真機上真的被殺 |
| 成本明確但不低 | journal 是一個新的持久化元件，有自己的交易邊界、加密、重放邏輯 |
| 會改變擷取路徑 | listener 的回呼要多做一次寫入，而那是在主執行緒上 |
| **它可能帶來比它解決的更大的問題** | 一個寫錯的 journal 會讓擷取**整個停擺** |

brief 的要求是：

> 如果 Prototype 缺乏足夠改善，維持設計文件，不接入正式管線。

**本輪的證據不足以說明它有足夠改善**，所以維持設計文件。

**在那之前**，記憶體佇列加上本文件的契約說明，
是誠實且足夠的狀態。
