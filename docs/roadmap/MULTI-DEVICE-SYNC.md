# 多裝置同步（未來規劃）

> **STATUS: PLANNING_ONLY**
>
> 本輪**沒有**實作任何同步功能。
> 這份文件只描述如果未來要做，會是什麼樣子，以及有哪些必須先解決的問題。

---

## 0. 先講清楚：這不是現在的 DHC Connector

| | 離線 DHC Connector（**已實作**） | 未來的自動同步（**只規劃**）|
|---|---|---|
| 方向 | 使用者手動匯出 / 匯入 | 裝置之間自動 |
| 觸發 | 使用者按下按鈕 | 背景排程 |
| 加密 | 使用者提供的密碼 | 裝置配對金鑰 |
| 網路 | **無**（App 沒有 INTERNET 權限）| 需要權限 |
| 資料流 | 使用者保管檔案 | 伺服器 / 直接連線 |
| 風險 | 使用者遺失密碼 | 憑證外洩、同步錯誤 |

**兩者完全不同。** 目前的 Connector 是**離線的、手動的、無網路的**，
這是刻意的：本專案的核心承諾是「資料不離開裝置，除非你親手把它交出去」。

自動同步會**打破**那個承諾，因此它需要一個**獨立的授權**，
而不是被當成 Connector 的延伸。

## 1. 必要元件

### 1.1 配對（Pairing）

兩台裝置透過 QR 碼或短碼建立信任。

| 項目 | 設計 |
|------|------|
| 配對碼 | 一次性、短時效、單次使用 |
| 傳輸 | 配對碼交換一把**裝置間金鑰** |
| 驗證 | 雙方顯示對方的**指紋**（金鑰的雜湊），使用者目視確認 |
| 撤銷 | 任何一端可以撤銷；撤銷後既有金鑰失效 |

### 1.2 裝置身分（Device Identity）

每台裝置有一個穩定的識別碼，**不是** Android ID（那會被重置），
也不是 Keystore 金鑰（那會在失效時消失）。

建議：一個存在 Keystore 裡的隨機識別碼 + 一個可在匯出中攜帶的短 human-readable 別名。

匯出格式裡的 `source_device_id` 已經是這個角色。

### 1.3 端對端加密（E2EE）

| 項目 | 設計 |
|------|------|
| 金鑰交換 | 配對時交換，之後不傳送 |
| 加密 | 沿用 DHC Connector 的 **PBKDF2-HMAC-SHA256 → AES-256-GCM** |
| 每則訊息 | 獨立 nonce |
| 標籤 | **不**使用叢集式標籤；每則訊息獨立，避免重複 nonce 的致命後果 |
| AAD | 綁定裝置身分與訊息 id，阻止重放 |

### 1.4 撤銷（Revocation）

- 撤銷一台裝置 → 它的金鑰被加入撤銷清單。
- 撤銷清單本身需要簽名，並且要被同步。
- **撤銷無法讓已被匯出的資料消失** —— 這是端對端加密的固有性質，
  必須在文件裡說清楚，不能含糊帶過。

## 2. 同步機制

### 2.1 增量游標（Incremental Cursor）

沿用 DHC Connector 的 cursor 概念：

```
cursor = "<received_at>:<message_id>"
```

但同步需要**跨裝置**穩定，所以游標不能只用本機的行 id。
`message_id` 是內容衍生的，所以它跨裝置穩定 —— 這正是它被設計成那样的原因。

### 2.2 墓碑（Tombstones）

刪除必須能同步。否則被刪除的訊息會在下一台裝置上復活。

```
tombstone = { message_id, deleted_at, deleted_by_device }
```

墓碑必須**保留**一段時間（與資料保留期限一致），否則過期的裝置
會把舊資料重新推回來。

### 2.3 衝突解決（Conflict Resolution）

同一則訊息在兩台裝置上都被修改的可能很低，但必須定義規則：

| 情況 | 規則 |
|------|------|
| 同一則訊息，內容相同 | 冪等，忽略重複 |
| 同一則訊息，內容不同 | **保留兩者**，並以 `message_id` 區分 —— 這正是內容衍生 id 的作用 |
| 一端刪除、一端修改 | **刪除優先**（墓碑的語意）|
| 兩端都修改 | 保留兩者；不做自動合併 |

**不做**自動內容合併。訊息是原始紀錄，不是可編輯的文件。

### 2.4 離線重播（Offline Replay）

離線期間產生的變更必須在重新連線後**依序重播**。

這需要一個**持久化的待送出佇列** —— 正是本專案目前在群組突發調查中
明確記錄為「尚未實作」的東西（見 `BURST-CAPTURE-ROOT-CAUSE.md` §5）。

所以：同步功能會**迫使**本專案先實作持久化 intake journal。
那是一件好事，但順序必須是先做 journal，再做同步。

## 3. Agent 讀取權限（Agent Read Permissions）

這是 DHC 情境下最重要的一個面向。

| 原則 | 說明 |
|------|------|
| **預設不可讀** | 同步的資料對 agent 是不可見的 |
| **明確授權** | 使用者必須逐項授權，或授權一個範圍 |
| **可撤銷** | 撤銷後 agent 立刻看不到 |
| **有稽核紀錄** | 誰在什麼時候讀了什麼 |
| **不自動交給 LLM** | 同步 ≠ 分享。分享是另一個明確的動作 |

目前的 DHC Connector 已經遵守這一點：匯出的檔案**不會**自動交給 LLM，
也不會自動上傳。使用者自己決定把它交給誰。

---

## 4. 資料保留（Data Retention）

| 項目 | 規則 |
|------|------|
| 來源資料 | 保留期限由**每台裝置**各自決定 |
| 同步佇列 | 送出後立即刪除（除非是重試佇列）|
| 墓碑 | 與資料保留期限一致 |
| 已撤銷裝置的資料 | 從佇列移除，但已匯出的副本無法召回 |

---

## 5. 實作順序（如果真的要做）

1. **持久化 intake journal**（本專案目前缺的那一塊）。
   沒有它，離線期間的資料會遺失，同步也就無從談起。
2. 裝置身分與金鑰管理的**介面**（先不實作傳輸）。
3. 兩台裝置之間的**手動**單向同步（用現有的 DHC 容器格式）。
4. 配對與金鑰交換。
5. 雙向同步與墓碑。
6. 撤銷。
7. Agent 讀取權限。

**第 1 步就有獨立價值**：它會讓本專案在行程被殺時不再遺失事件。
那個問題在群組突發調查中已經被明確記錄（見 §2.4）。

---

## 6. 明確不做的事

- **不做**雲端備份服務。
- **不做**即時推送。
- **不做**自動把訊息交給任何 LLM。
- **不做**為了同步而放寬 App Lock 或通知存取的權限。
- **不做**讓同步成為預設功能。
