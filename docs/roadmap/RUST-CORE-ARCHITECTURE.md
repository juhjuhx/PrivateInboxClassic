# Rust Core 架構（RUST-CORE-ARCHITECTURE）

> 分支：`fix/x200pro-notification-burst`（v0.4.4）
> 狀態：**RESEARCH_ONLY** —— 沒有任何一行 Rust 進入生產路徑。
> 本文件是**研究**，不是遷移計畫的承諾。

---

## 1. 結論先講

**本專案目前不需要 Rust。**

理由不是語言偏好，而是證據：

| 依據 | 數值 | 來源 |
|------|------|------|
| 回呼延遲 p50 | 0.04 ms | `LatencyBenchmarkInstrumentedTest` |
| callback p95 | 見基準輸出 | 同上 |
| 佇列等待 p99 | 2,091 ms（500 則突發）| `BURST-CAPTURE-ROOT-CAUSE.md` |
| 加密成本 | 每次寫入一次 AES-GCM | `CryptoStore.kt` |

**Rust 能改善的是「純邏輯的重複計算」** —— 訊息正規化、分類、去重。
而實測顯示這些都不是瓶頸：瓶頸是**磁碟 I/O 與排程**，不是運算。

**唯一一個真實的跨語言一致性問題**（base64 換行造成兩邊的訊息 id 不同）
在 v0.4.3 已經用**更好的測試**解決了，而不是靠把實作換成 Rust。

---

## 2. 那 Rust 什麼時候才有意義

**當同一份邏輯需要在兩個以上的地方執行，而且它出錯的時候會造成資料損失。**

那就是 **DHC Connector 的匯出契約**：
Android 產生訊息 id 與分類，Python 匯入端要能重現同樣的結果。
v0.4.3 的跨語言測試找到 base64 換行的缺陷，就是這個風險的實例。

**但**即使如此，先把跨語言測試做完整，比引入一個新語言便宜得多。

---

## 3. 保留在 Kotlin 的部分

這不是偏好，是**技術上做不到**或**風險不划算**：

| 元件 | 原因 |
|------|------|
| `NotificationListenerService` | Android 系統 API，Rust 無法直接使用 |
| `ContentResolver` / 媒體讀取 | 需要 Android Context 與 URI 授權 |
| `NotificationManager` | 同上 |
| **Android Keystore** | **硬性邊界。** 金鑰操作透過 Android Keystore API；Rust 若要存取需要 JNI 進入同一個 provider。**一旦金鑰操作進入 Rust，「金鑰不離開裝置」就需要額外論證** |
| 原生 Android UI | Telegram Classic 風格是原生 View，不是 Compose |

---

## 4. 可以遷移的部分（若真的要做）

| 模組 | 為什麼它適合 | 風險 |
|------|-------------|------|
| 訊息正規化 | 純函式、規則明確、已有測試 | 低 |
| 去重識別碼 | 跨語言必須一致的地方 | 中 —— 改錯會造成合併或重複 |
| 對話識別 | 純邏輯 | 低 |
| 分類 | 已有 20 項測試可當契約 | 低 |
| 可攜式匯出資料契約 | 與 DHC 共用 | 中 —— 契約變更是破壞性變更 |

## 5. 綁定方式：UniFFI vs JNI

### 5.1 UniFFI

| 項目 | 評估 |
|------|------|
| 授權 | **MPL-2.0**（實測，非 MIT/Apache）|
| 維護狀態 | 活躍（最後推送 2026-10-16，5,042 stars）|
| 型別安全 | 自動產生 Kotlin 資料類別 |
| 錯誤處理 | 以例外呈現 |
| 建置 | 需要額外步驟 |

**MPL-2.0 是檔案層級的 copyleft**：使用 UniFFI 沒問題，
但**修改了 UniFFI 的檔案**就必須以 MPL-2.0 發布那些檔案。
本專案只使用產生的綁定，不修改 UniFFI 本身 —— **這個判斷必須在導入時重新確認**。

### 5.2 手寫 JNI

完全控制，但型別安全與錯誤處理都要自己維護。
**錯誤面更大**，而這個專案的痛點正是「錯誤面」。

### 5.3 建議

**UniFFI。** 本專案最在意的是正確性，不是建置速度。

### 5.4 呼叫成本（需要量測，不能推測）

| 呼叫 | 預期成本 | 為什麼需要量 |
|------|---------|------------|
| 純函式（正規化） | 數百奈秒 | JNI 邊界成本可能超過函式本身的成本 |
| 涉及字串的配置 | 數微秒 | 字串複製是主要成本 |
| 大量呼叫 | 可能比 Kotlin 慢 | 這正是「Rust 更快」的假設可能不成立的原因 |

**在量測之前不能宣稱 Rust 更快。**
本專案已經有一次這樣的教訓（見 `PERFORMANCE-BASELINE.md` 的金鑰快取實驗：
實測比原來**慢 1.38 倍**，所以被回滾）。

## 6. 授權與 DHC 的邊界

DHC 是 **AGPL-3.0**。

**如果 Rust 核心要與 DHC 共用原始碼，那個核心必須是 AGPL。**

可能的解法：

| 解法 | 可行性 |
|------|--------|
| Rust 核心獨立發布（如 Apache-2.0），DHC 以 process 或動態連結使用 | 可行，但增加建置複雜度 |
| Rust 核心保持 AGPL，Private Inbox 透過 process 呼叫 | 可行，但引入了一個 AGPL 相依 |
| 兩邊各自實作，以跨語言測試保證一致 | **最簡單，也最安全** |

**目前的最後一個選項已經被驗證可行**（v0.4.3 的跨語言 fixture 測試）。

## 7. 二進位大小

Rust 的靜態連結會帶來每個 ABI 一份的 .so。

| 項目 | 估算 |
|------|------|
| 一個只含純邏輯的 crate | 每個 ABI 約 200 KB – 1 MB |
| 目前的 APK | 5.9 MB（無原生相依）|
| 若加入 Rust | 每個 ABI 增加 1–3 MB（含除錯資訊）|

**這個成本在沒有可證明的效能收益時不划算。**

---

## 8. Crash 邊界

Rust 的 panic 會導致進程崩潰，除非用 `catch_unwind` 包起來。
Kotlin 的例外預設是受控的。

**對於一個在背景持續擷取通知的 App，一個偶發的 Rust panic 會停止所有擷取** ——
正是本專案已經受過一次教訓的那種故障。

必須用 `catch_unwind` + 明確的 fallback 來包裝每一個邊界。

---

## 9. 觸發條件

**只有當下列全部成立時，才應該重新評估 Rust：**

1. Kotlin 的實作被證明**正確性不足**（不是效能不足）。
2. 同一份邏輯**必須**在兩個以上的地方執行，且無法用測試保證一致。
3. 跨語言測試**無法**覆蓋那個風險。
4. 有**量測**顯示 Rust 的方案真的更好。

目前**沒有**一條成立。
