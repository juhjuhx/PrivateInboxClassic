# 圖片擷取未來工作（MEDIA-CAPTURE）

> **STATUS: DEFERRED**
>
> 本輪**沒有**新增任何圖片格式適配器、**沒有**修改照片 UI、
> **沒有**啟動任何逆向工程、**沒有**新增影像函式庫。
>
> 唯一的要求是：**現有的圖片功能不得破壞文字通知擷取。**
> 這個要求已由既有的測試覆蓋（見 §5）。

---

## 1. 現有能力

| 項目 | 現況 |
|------|------|
| 擷取來源 | `EXTRA_PICTURE`（Bitmap）、`EXTRA_PICTURE_ICON`（API 31+）、`MessagingStyle.Message.dataUri`（`image/*`） |
| 讀取限制 | 只接受 `content://`；`file://` 與 `http(s)://` 一律拒絕 |
| 逾時 | 2 秒上限（慢的 content provider 不能卡住通知回呼） |
| 大小上限 | 輸入 8 MiB；預覽 ≤ 700 KiB |
| 降級 | 最長邊 1280 px；`inSampleSize` 確保解碼後 ≤ 2048 px |
| 格式驗證 | magic byte（JPEG/PNG/GIF/WebP/HEIC-ISOBMFF）+ 宣告 MIME |
| EXIF | 讀取方向旋轉，**其餘 EXIF 全部丟棄**（不保留 GPS/機型） |
| 加密 | AES-256-GCM，AAD 為 `<package>:image` |
| 儲存 | App 私有資料庫的 BLOB，**不是**檔案系統上的圖片 |
| 顯示 | 縮圖（480 px 解碼）+ 全螢幕（1600 px 解碼）+ 純框架縮放檢視器 |

---

## 2. 已知限制

| 限制 | 影響 |
|------|------|
| 只保存預覽 | 不是原檔；EXIF 丟失；GIF 變成靜態；動態照片無法重建 |
| 只在通知附帶影像時才有 | LINE / Instagram 常只推文字「傳送了一張照片」 |
| 影像 URI 授權短暫 | 可能在讀取前就被撤銷 |
| 沒有 HEIF 轉碼 | 部分相機格式可能解碼失敗（但只影響該張照片，不影響文字） |
| 沒有影片 | `video/*` 明確不處理 |
| 沒有縮圖快取 | 每次捲動都重新解密解碼（見 `PERFORMANCE-BASELINE.md` 的待改善項） |

---

## 3. 未來研究候選

| 候選 | 解決什麼 | 風險 |
|------|----------|------|
| **縮圖快取**（記憶體內 LRU） | 解決列表捲動時重複解碼 | 記憶體佔用；快取失效邏輯 |
| **分頁 + 延遲解碼** | 只解碼可見範圍的縮圖 | 實作複雜度；與「先載入」的取捨 |
| **AVIF/HEIC 解碼** | 支援更多相機格式 | 函式庫大小；Android 內建的支援度依版本而異 |
| **保留有限 EXIF** | 例如保留方向與拍攝時間 | 隱私：EXIF 可能含 GPS。**必須逐欄白名單** |
| **原始檔案（唯讀）** | 保留完整原檔 | 大幅增加儲存空間；需要新的保留期限政策 |
| **MIME 白名單** | 明確宣告支援的格式 | 過於嚴格可能漏掉新格式 |

## 4. 依賴條件

任何影像相關的工作都需要先回答：

1. **是否會新增第三方函式庫？**
   若會，必須先做授權與供應鏈審查（見 `SECURITY-AUDIT.md` 的相依稽核章節）。
   偏好使用 Android 內建能力（`BitmapFactory`、`ImageDecoder`、
   `androidx.exifinterface`）而非新增相依。

2. **是否會改變儲存格式？**
   若會，需要資料庫遷移，且**必須是加性的**（見
   `MIGRATION-STRATEGY.md`）。

3. **是否會改變保留期限的語意？**
   保留原檔會讓資料庫體積成長一個數量級，保留期限政策必須重新評估。

4. **是否會讓影像處理回到通知回呼？**
   **絕對不可以。** 目前的保證是：回呼內只讀 bytes，解碼在背景執行緒。
   任何最佳化都不得破壞這條界線。

## 5. 本輪的新證據：媒體路徑已被量測

上一輪的群組突發調查（見 `docs/reliability/BURST-CAPTURE-ROOT-CAUSE.md`）
第一次量到了媒體路徑對擷取管線的影響。

**TEST-F** 開啟照片擷取，**TEST-H** 關閉，兩者比較：

| F | 開 | 25 | 25 | 25 | 0 | 1,160 ms |
| H | 關 | 100 | 100 | 100 | 0 | 542 ms |
| A | 開 | 20 | 20 | 20 | 0 | 149 ms |

**開啟照片擷取沒有讓任何訊息遺失**（unaccounted 全部為 0）。
在突發情境下，媒體管線的影���是可以量測的，而且**不構成漏接的原因**。

## 6. 驗收方法

### 6.1 現有保障（不得退步）

| 測試 | 現況 |
|------|------|
| `imageIsStoredEncryptedAndDecryptsBack` | 影像密文 ≠ 明文，解密後位元組一致 |
| `ImageCaptureTest`（8 項） | magic byte 驗證、MIME rescue、非影像拒絕 |
| `malformedSourcePreferenceDoesNotCrashTheListener` | 畸形資料不讓監聽器崩潰 |
| `listenerSurvivesAMalformedNotification` | 同上 |
| `emptyNotificationDoesNotCrash` | 空通知不崩潰 |

### 6.2 影像功能改動時必須新增

- 超大圖片（> 2048 px、> 8 MiB）的降級行為。
- 損毀圖片的錯誤狀態（UI 必須顯示錯誤，不能空白）。
- 失效 URI（授權已撤銷）不得 Crash。
- 圖片失敗時**文字仍然入庫**。
- 記憶體峰值：解碼一張 1280 px 圖片不得造成 OOM。

### 6.3 量測

影像相關的改動必須附上量測數字，方法見
`../engineering/PERFORMANCE-BASELINE.md`：

- 解碼 1 張 / 100 張 / 1000 張縮圖的耗時。
- 記憶體峰值。
- 通知回呼耗時（必須維持在個位數毫秒）。

## 7. 明確不做的事

- **不做 REA 逆向分析。**
- **不做格式的私有/專有格式適配。**
- **不為了「支援更多格式」而新增大型影像相依。**
- **不在這條路上投入超過必要的工作。** 照片是輔助功能，文字擷取才是核心。

---

## 8. 優先序建議

若未來真的要做，建議順序：

1. **縮圖快取 + 分頁** — 直接改善日常使用體感，且不碰格式支援。
2. **EXIF 逐欄白名單** — 小幅實作，但隱私風險要仔細評估。
3. 其餘（AVIF、原檔）— 需求出現時再談。
