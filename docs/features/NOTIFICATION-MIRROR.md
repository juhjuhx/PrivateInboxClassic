# 可選的通知鏡像（Optional Notification Mirror）

> **STATUS: DESIGN_ONLY**
>
> 本輪**不實作**這個功能。這份文件是規格，不是承諾。
> 現有的通知擷取路徑**完全不受影響** —— 鏡像只是「保存成功之後」多一個可選的副作用。

---

## 1. 目的

目前 Private Inbox 是一個**被動的存檔**：使用者要打開 App 才看得到已保存的訊息。
鏡像功能讓使用者在**收到新通知的當下**，由 Private Inbox 自己也發一則通知，
把使用者拉回 App 檢視該則副本。

它**不是**轉發功能：通知的內容是 Private Inbox 自己產生的摘要，
指向 Private Inbox 自己的畫面。

---

## 2. 設計紅線

這些是硬性限制，不是建議：

| 紅線 | 理由 |
|------|------|
| **預設關閉** | 使用者未明確同意前，不產生任何額外通知 |
| **不得冒充來源 App** | 通知必須清楚標示來自 Private Inbox。模仿 LINE 的通知外觀 = 冒充，會造成實際的傷害（使用者可能以為是對方真的在說話） |
| **不得產生通知迴圈** | Private Inbox 自己的通知會被系統投遞 → 監聽器收到 → 觸發保存 → 再鏡像 → 無限迴圈。**必須排除自身套件名** |
| **不得重複通知** | 同一則訊息只鏡像一次 |
| **不得在保存失敗時鏡像** | 只在 `SaveResult.NEW` 時鏡像；`DUPLICATE` 與 `FAILURE` 都不鏡像 |
| **不得洪水式轟炸** | 需要速率限制（例如每分鐘最多 N 則） |
| **鎖屏不得洩漏內容** | 預設為通用預覽；完整內容必須是明確 opt-in |
| **顯示詳細內容前必須通過 App Lock** | 鏡像通知點進去仍要驗證裝置身分 |

### 通知迴圈的具體防護

現有的 `CapturePolicy.allowed()` 使用白名單機制，自身套件名
`tw.personal.privateinbox` **不在**白名單中，所以即使鏡像通知被系統投遞，
也不會被保存。**這個防護已經存在且必須保留。**

但仍需第二道防護，因為 `SelfTestNotifier` 已經把自身套件名加入白名單：

1. 鏡像通知使用**獨立的 notification id 區間**，與自我測試通知不同。
2. 鏡像前先檢查 `sbn.packageName != BuildConfig.APPLICATION_ID`。
3. 監聽器收到自身套件的通知時，直接忽略（不進白名單路徑）。

## 3. 使用者設定

```
設定 → 通知鏡像

  [ ] 產生鏡像通知                    預設關閉

  顯示內容
  ( ) 通用預覽（推薦）                鎖屏只顯示「Private Inbox：1 則新訊息」
  ( ) 完整預覽                        顯示寄件人與摘要，需要明確 opt-in

  [ ] 靜音通知                        使用無聲 channel
  [ ] 點擊後開啟對話                    直接跳到該則訊息所在的對話
  [ ] 顯示詳細內容前要求解鎖            沿用 App Lock

  速率限制：每分鐘最多 [3] 則
```

**不提供沒有實際作用的開關。** 每一個選項都必須對應可觀察的行為差異。

---

## 4. 通知規格

| 項目 | 規格 |
|------|------|
| Channel | 獨立的 `notification_mirror` channel，`IMPORTANCE_DEFAULT` |
| 標題 | `Private Inbox`（**永遠是這個**，不顯示來源 App 名稱以外的冒充資訊） |
| 內容（通用預覽） | `1 則新訊息` 或 `3 則新訊息` |
| 內容（完整預覽） | `Alice: 晚上一起吃飯嗎？`（可 opt-in） |
| 小圖示 | 應用程式自己的圖示 |
| PendingIntent | 開啟 MainActivity 對應的對話 |
| 自動取消 | 是（autoCancel） |
| 設定顯示通知 | 由使用者控制 |
| 鎖屏可見性 | 預設 `VISIBILITY_PRIVATE`（鎖屏只顯示通用預覽） |

### 為什麼不顯示來源 App 的名稱

顯示「LINE: Alice」看起來像 LINE 自己的通知。使用者在鎖屏上會誤以為
是 LINE 通知，實際上這是 Private Inbox 的存檔。
正確的做法是顯示「Private Inbox」，讓使用者知道這是存檔提醒。

## 5. 實作位置

| 階段 | 位置 | 說明 |
|------|------|------|
| 觸發 | `PrivateNotificationListener.capture()` 的 worker 迴圈內 | 只有 `SaveResult.NEW` 才觸發 |
| 產生 | 新的 `MirrorNotifier` 物件 | 與 `SelfTestNotifier` 分離，但共用 channel 建立邏輯 |
| 設定 | `LocalSettings` 新增一組鍵 | 全部預設為關閉 |
| UI | 設定頁新增一個區段 | 與既有開關風格一致 |

### 資料流

```
notification posted
  → capture() → worker
    → db.save() → SaveResult.NEW
      → 檢查鏡像開關
        → 檢查速率限制
          → MirrorNotifier.post()
```

**每一個環節都必須失敗安全**：鏡像的任何錯誤都不能影響保存流程。
所以 `MirrorNotifier.post()` 必須被 `runCatching` 包住。

---

## 6. 需要實作的測試

| 測試 | 驗證內容 |
|------|----------|
| 鏡像預設關閉 | 安裝後不產生任何鏡像通知 |
| 開啟後只對 NEW 鏡像 | `DUPLICATE` 與 `FAILURE` 不產生通知 |
| 自身通知不被保存 | 鏡像通知回到監聽器時被忽略（無迴圈） |
| 速率限制生效 | 短時間內大量通知只產生 N 則鏡像 |
| 通用預覽不洩漏內容 | 鎖屏文字不含寄件人與內容 |
| 完整預覽需明確 opt-in | 未 opt-in 時只有通用預覽 |
| 鏡像失敗不影響保存 | 通知發送失敗時資料仍已入庫 |

## 7. 未來實作計畫

1. 新增 `MirrorNotifier`，與 `SelfTestNotifier` 並列。
2. `LocalSettings` 加入鏡像設定，預設全部關閉。
3. 在 `capture()` 的 worker 中，於 `SaveResult.NEW` 之後呼叫。
4. 設定頁新增區段。
5. 加入上列 7 項測試。
6. 觀察一個版本後，再考慮是否預設開啟「通用預覽」。

**風險評估**：主要風險是通知洪水與使用者騷擾。兩者都由速率限制與
預設關閉來緩解。**不建議**在第一版就預設開啟。

---

## 8. 為什麼這輪不做

1. 這個功能的價值取決於使用者的實際需求，而目前沒有明確需求。
2. 它增加了「應用程式產生通知」這條新路徑，而這條路徑正是通知迴圈的溫床。
   在核心擷取路徑已經穩定之前加入它，風險不划算。
3. 本輪的優先級是資安收斂與效能基準。
