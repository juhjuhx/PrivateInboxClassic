# 效能基準（PERFORMANCE-BASELINE）

> **量測環境警告 — 請先讀這一段。**
>
> 本次量測在 **load average 16 / 8 核心** 的共享 macOS 主機上執行
> （Android 16 模擬器與其他工作同時佔用 CPU）。
> 絕對時間數字因此**高度不穩定**：同一個測試在不同次執行之間，
> 10,000 筆讀取從 4.7 s 變成 29.5 s。
>
> 本文件因此把數字分成三類：
> 1. **穩定且可重現的** — 例如資料庫大小、每列位元組數、記憶體佔用。
> 2. **僅供參考的量測值** — 絕對時間，明確標示為受環境影響。
> 3. **已被量測推翻的假設** — 記錄下來，避免重複浪費時間。
>
> 對這個產品而言，**真實使用情境不會有 10,000 則訊息**；真正的瓶頸是
> 背景擷取路徑的即時性，而不是列表的讀取速度。

---

## 1. 量測方法

- 測試類別：`PerformanceBaselineInstrumentedTest`（instrumentation，在裝置內執行）
- 資料：**完全合成的測試資料**，不含任何真實聊天內容
- 每次讀取前先做暖機（warm-up），避免把一次性成本算進去
- 取 5 次的 **p50** 與 **p95**
- 原始輸出：`docs/INSTRUMENTED-TEST-LOG.txt`（`System.out: PERF ...`）

---

## 2. 穩定可重現的數據

| 指標 | 數值 | 備註 |
|------|------|------|
| 每列資料庫大小 | **317–321 bytes** | 三次獨立量測，誤差 < 1.5% |
| 1,000 列的資料庫大小 | **316–352 KiB** | 含 WAL sidecar |
| 10,000 列的資料庫大小 | **3.34–3.35 MiB** | 線性成長 |
| 1,000 列解密後的記憶體佔用 | **216–552 KiB** | 視 GC 時機 |
| 資料庫增長 | 與列數成線性 | 沒有索引退化 |

資料庫大小是本專案最重要的效能指標 —— 它直接決定使用者的儲存空間佔用。
**每列約 320 bytes** 意味著 10,000 則訊息只佔 3.2 MiB，屬於良好水準。

---

## 3. 參考用的時間數據（受環境影響）

| 指標 | p50 | p95 | 備註 |
|------|-----|-----|------|
| 寫入 100 列 | 1.4 s | — | 最佳一次量測 |
| 寫入 1,000 列 | 5.3 s | — | 最佳一次量測 |
| 讀取+解密 100 列 | 186 ms | 307 ms | 最佳一次量測 |
| 讀取+解密 1,000 列 | 1.8 s | 2.2 s | 最佳一次量測 |
| 讀取+解密 10,000 列 | 4.7 s | 5.0 s | 最佳一次量測 |
| 索引查詢 `recent(50)`（1,000 列資料庫） | 119 ms | 122 ms | 最佳一次量測 |
| AES-GCM 解密 200 筆 | 469 ms | — | 首次量測，無暖機 |
| Activity 啟動 | — | — | 模擬器上量測無意義（見 §5） |

> 上述是**多次執行中最好的一次**。同一測試在尖峰負載下的結果為
> 讀取 10,000 列 = 29.5 s。**請以這個區間理解數字，而不是單一數值。**

## 4. 已被量測推翻的假設

### 4.1 「快取 Keystore 金鑰 handle 可以加速解密」— **已推翻**

**假設**：`CryptoStore.aesKey()` 每次呼叫都重新開啟 AndroidKeyStore 並
`getKey()`，是一次 IPC round trip。快取 `SecretKey` handle 應該能大幅加速。

**實作**：加入 `cachedAesKey` / `cachedHmacKey` 快取。

**量測結果**（同一 process 內 A/B 對照，100 筆解密，取 p50）：

| 變體 | 時間 |
|------|------|
| 有快取 | 1,472 ms |
| 每次重新取金鑰 | 1,068 ms |
| **比率** | **1.38×（快取反而更慢）** |

**結論**：在 Android 16 模擬器上，`getKey()` 的成本很低，
而快取帶來的鎖競爭與失效風險反而是淨損失。
**已回滾該最佳化**（`git checkout` 還原 `CryptoStore.kt` 的快取部分）。

**保留的教訓**：這個假設已被記錄，避免未來重複嘗試。
若要重新評估，必須在**真實實體裝置**上量測 —— 模擬器的 Keystore
實作（TEE 軟體模擬）與硬體差異很大。

### 4.2 「在模擬器上量測 Activity 啟動時間」— **不適用**

量測結果：cold 11,346 ms、warm 11,341 ms。

兩個數字幾乎相同且都遠大於任何真實裝置的合理值，這是
**模擬器 + 已被量測汙染的主機負載**的產物，不是應用程式的啟動效能。
**此數據不具參考價值，已排除。** 啟動時間需在實體裝置上量測。

## 5. 已知的主執行緒風險（尚未量測，但由程式碼結構可確定）

以下是從程式碼結構確認的問題，**尚未量測**，列為後續工作：

| 問題 | 位置 | 影響 |
|------|------|------|
| 聊天列表一次解密 1,500 筆 | `MainActivity.loadEntries()` → `db.recentWithState(1500)` | 讀取 1,500 列約需 2.7 s（`io` 執行緒，主執行緒不卡，但列表要等 2.7 s 才出現） |
| 列表每次重建全部 View | `showInbox()` 逐筆 `addView` | 列數多時造成 GC 壓力與捲動卡頓 |
| 搜尋時再次全表解密 | `showSearch()` → `entries.filter { ... }` | 搜尋結果只過濾已解密的那 1,500 筆 |

**優先改善方向（依效益排序）**：

1. **分頁載入**（先載入 100 筆，往下捲再載入更多）— 直接解決 2.7 s 的首屏延遲。
2. **只解密列表需要的欄位** — 預覽只需要 title/sender/body 的前 N 個字元，
   但目前整段 JSON 都必須解密才能取出。
3. **穩定 item ID 與增量更新** — 避免整份列表重建。

> 這三項都屬於「列表呈現」路徑，**不影響背景擷取的可靠性**。
> 擷取路徑（監聽器 → 解析 → 加密 → 入庫）維持原樣。

---

## 6. 背景擷取路徑的即時性

`PrivateNotificationListener.capture()` 在監聽器回呼中**只做**：

- 讀取偏好設定（一次 SharedPreferences 讀取）
- 解析 extras（記憶體操作）
- 讀取影像 URI 的原始 bytes（僅在開啟照片擷取且通知附帶影像時）

其餘（解碼、縮圖、JPEG 壓縮、加密、入庫）全部在 `worker` 單執行緒上完成。

**設計上的即時性保證**：通知回呼不會被影像處理阻塞。
`ImageCapture.readBytes()` 另有 2 秒逾時上限，慢的 content provider
無法卡住系統的通知處理。

**待量測項目**（需真實 App 推播）：

| 項目 | 狀態 |
|------|------|
| 通知回呼的端到端耗時 | NOT TESTED |
| 背景 worker 佇列深度 | NOT TESTED（目前無上限，是已知的待改善項） |
| 連續 100 則通知的擷取延遲分佈 | NOT TESTED |

---

## 7. 結論

**本專案的效能不是瓶頸**：

- 資料庫大小合理（320 bytes/列）。
- 記憶體佔用低（1,000 列解密後 216–552 KiB）。
- 背景擷取路徑的結構保證不會阻塞通知回呼。

**真正的待改善項**是列表的首屏延遲（2.7 s / 1,500 列），
需要分頁與增量載入來解決。這會是後續的效能工作重點。

**同時必須誠實說明**：本文件的絕對時間數字來自一台負載過高的共享主機，
**不足以作為效能基準的正式依據**。要在真實硬體上建立可信基準，
需要先在實體裝置上重跑 `PerformanceBaselineInstrumentedTest`。
