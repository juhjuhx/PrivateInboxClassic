feat: the DHC Connector v0.2 offline export flow, and a real interop bug

THE INTEROP BUG.

The cross-language check (python exports -> android validates) found a defect
that only shows up across the two implementations: the message id differed by
a single trailing character.

  python:  msg_vAqh2ijUIiDWkO4grhsE
  android: msg_vAqh2ijUIiDWkO4grhsE\\n

Android's Base64 appends a trailing NEWLINE unless NO_WRAP is given. The
digest itself was identical, so the bug was invisible to any test that only
checked the Android side. The consequence is real: the same message would
get two different ids depending on which side computed it, and the import
would NOT be idempotent across the two.

The exporter now uses URL_SAFE | NO_PADDING | NO_WRAP and trims the padding
and line endings, so the two sides agree byte for byte.

The other direction (android exports -> python imports) was already proven by
the host-side script; the new fixture test proves the reverse.

THE EXPORT FLOW.

The v0.1 exporter could produce a bundle, but there was no way for a user to
get one: no UI, no file, no passphrase. v0.2 adds the whole offline loop:

  1. The user chooses WHAT to export. A plan is built and SHOWN first, with
     the counts and the source names, and no content in the summary.
  2. The user chooses WHERE, through the Storage Access Framework. The app
     never picks a path itself.
  3. The user provides a PASSPHRASE. It is held in a CharArray that is
     zeroed as soon as the export finishes. It is never stored, never logged
     and never included in the bundle.
  4. The bundle is written, encrypted, to the chosen destination.

The plan supports all the sources, a selected subset, and a date range, and
it is incremental-aware. The passphrase is not recoverable: the confirmation
dialog says so.

The app still has no INTERNET permission, so an export cannot leave the
device by accident.

Also fixed: a stray NUL byte in two Kotlin string literals, which made the
files binary to git and to every text tool.
